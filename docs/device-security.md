# Browser compatibility and network isolation gates

Current safety mode keeps JavaScript disabled on every platform. Android and iOS do not have a verified public equivalent of ArkWeb's advanced security mode disableNonProxyUDP option; JavaScript injection or removing a WebRTC global is not a reliable network policy. ArkWeb's advanced-security option also depends on engine/OS support and must be tested before a JavaScript-enabled mode is offered. Do not claim that a WebView proxy override alone blocks every UDP or DNS path.

iOS: set Network.framework CONNECT proxy credentials as before and handle a WKNavigationDelegate authentication challenge only if NSURLProtectionSpace identifies the exact loopback proxy host/port and HTTP Basic, with zero previous failures. Origin authentication is canceled except ordinary system server-trust evaluation. This is a fallback, not a guaranteed fix for WebKit versions that never deliver proxy challenges (WebKit bug 264309). Android and ArkWeb still scope credentials to the expected loopback host and empty realm; if the engine supplies another host, authentication remains blocked. Debugging explicitly disabled on Android and OHOS.

The Android device-auth CI now uses a controlled TLS origin and CONNECT relay running on the runner, reached via adb reverse. The relay only forwards the reserved browser-tls-probe.invalid hostname to the local origin, never resolves public domains. Each run generates a fresh CA and server certificate. The trust anchor is scoped to the test hostname in the temporary project's debug source set only. Normal app artifacts have no test CA, no test private key, and still cancel SSL errors. The test expects a real HTTPS redirect to /verified, and runner-side events independently prove an authenticated CONNECT and TLS origin request. An unmatched domain must report failure and must not reach the controlled upstream. This is not a packet capture or proof that every DNS/UDP path is isolated. JavaScript remains disabled; actual JavaScript enablement requires the network isolation gates below. Device CI is separate from ordinary UI builds. iOS and OHOS equivalent device setup is not yet automated.

Before enabling JavaScript or declaring production readiness:
1. Authenticate through the actual core on each OS/engine version. Confirm bad credentials fail and no credentials go to origin challenges.
2. Use an owned HTTPS origin with valid certificate and owned DNS, STUN/TURN and UDP endpoints. Observe egress at a controlled gateway with direct, proxy, and unmatched domains, including iframe, redirect, workers, downloads and WebRTC. Use unique test labels; log no real URLs or subscription tokens.
3. Stop the core during navigation and repeat with a fresh renderer; no unapproved direct traffic may appear. Verify a separate app still uses its original network route.
4. Only enable JavaScript on a platform after its enforcement mechanism and packet-capture tests pass. No system VPN or TUN.

Android API 35 integration run 45973769449 passed the allowed HTTPS redirect assertion but failed waiting for the unmatched-domain error text. The cause of the missing UI error is not proven. The follow-up handles main-frame HTTP errors in addition to network/TLS errors, prevents failed-page callbacks from entering history, records a loading/completed status, and prints the controlled relay events even when Flutter assertions fail. The REJECT assertion has not been removed or weakened. JavaScript remains disabled pending a green run and isolation validation.
